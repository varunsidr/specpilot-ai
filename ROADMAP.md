# Roadmap

The project currently delivers a local requirement-to-plan workflow. This roadmap lists outcomes in dependency order; it is not a release promise. A stage is complete only when its acceptance checks pass on both configured repositories.

The agreed sequence is documented in [FUTURE_WORKFLOW.md](FUTURE_WORKFLOW.md): profile source, retrieve and audit evidence per criterion, assess, draft, verify, then add Git/diff review and isolated execution. As of 2026-10-10, rough engineering-scope estimates are 70% complete for the local planning milestone and 30% for the full platform. These percentages do not represent model accuracy.

| Stage | Status | Outcome and acceptance checks |
| --- | --- | --- |
| 1. Local planning foundation | Done | Validate requirements, read both repos, retrieve line-numbered chunks, count model tokens, call local Ollama, validate paths, save runs, and evaluate retrieval on real requirements. |
| 2. Evidence quality | In progress | Backend evidence IDs supply exact quotes. Assessment precedes drafting; gaps stay fixed, review checks each scenario, and one reviewed correction is allowed. Follow-ups retain cited and previously requested evidence, with bounded handling of redundant requests. Nineteen source-fingerprinted cases are implemented. Establish reliability on held-out cases with independent source review before patch generation. |
| 3. Git provenance and proposed diffs | Planned | Record both repository commit IDs and dirty state in every run. Produce a reviewable patch tied to those commits. A plan may recommend new files, but applying a patch requires explicit review. |
| 4. Isolated application and checks | Planned | Apply an approved patch in separate branches or worktrees. Select impacted Playwright tests from the diff, run project checks, and attach logs and exit codes to the run. Never execute free-form model commands. |
| 5. Dashboard workflow | Planned | Show requirement, selected evidence with line numbers, plan, proposed diff, review decision, and check results. Use an authenticated backend proxy before access outside the local machine. |
| 6. Wider operation | Later | Add job isolation, auth and authorization, retention rules for source-bearing artifacts, structured logs, failure recovery, and a storage/index design for larger repositories. |

## Near-term tasks

The first implementation now adds deterministic syntax profiles and structure-aware JS/TS/JSX/TSX chunks, with a bounded text fallback and versioned cache migration. TypeScript and 41 tests pass. Evaluation now rejects CPU-offloaded or unverifiable embedding/planner placement and reports hardware blocks separately. A three-case frozen-source retrieval smoke completed within budget with full GPU embedding placement: quantity evidence coverage remains complete and selected file recall improves for the enhancement, while shipping evidence coverage remains zero. These changes do not establish improved plan quality; see [evals/README.md](evals/README.md).

2. Obtain a live missing-feature plan that matches a source-reviewed reference. A manually authored quantity reference passes exact citation validation and ten independent boundary/guard checks; see [evals/QUANTITY-REVIEW.md](evals/QUANTITY-REVIEW.md). The reference remains a manually authored check, not a live-model success.
3. The private assessment audit requires one support/relevance check per cited ID and a source or policy question for each unknown criterion. Policy-only uncertainty cannot trigger source requests; unresolved questions in drafts are rejected. TypeScript and 52 tests pass. The four reserved live cases match only 1/4 expected outcomes and reject three assessments; the separate development planner check matches 1/3. Missing-policy cases still fail to return business questions, and accepted audits can misdescribe cited lines. These checks enforce the model's stated audit consistently; independent source review must establish whether its claims are true. Reserved inputs were authored before this increment and were not used to tune it; independent gold review remains pending.
4. Capture repository commit IDs before retrieval and report when files change during planning. Use those IDs when generating a patch.
5. Build the diff preview and review step before any write to either external repository.
6. Connect test selection and execution only after patch review and isolation are working.
